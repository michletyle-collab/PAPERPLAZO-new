# PAPERPLAZO

PAPERPLAZO is a locally runnable premium paper-packaging commerce project with two deliberately separate front ends:

- Customer app: `http://127.0.0.1:5000/`
- Private admin app: `http://127.0.0.1:5000/admin/`

Both use one Flask REST API and one database. The customer site never embeds the administrator UI, and the administrator API rejects non-admin tokens.

## What is implemented

- Responsive customer storefront based on the supplied forest-green / kraft / cream design direction.
- Live catalog with search, categories, price sorting, product details, stock labels, related products, favourites, and image support.
- Guest cart persistence in local storage, authenticated server cart persistence, and automatic cart view after adding a product.
- Customer registration, login, hashed passwords, profile, saved delivery addresses, order history, invoice download, reorder, and private status tracking.
- Cash-on-delivery order creation with server-side cart/stock validation. Stock is deducted only when an administrator confirms the order; cancellation restores deducted stock.
- Custom-bag request with dimensions, GSM, colour, handles, printing notes, logo upload, quote pricing, document upload, and customer accept/reject decision.
- Separate admin login; live order, product, image, category, inventory, customer, quotation, notification, contact-message, and analytics screens.
- SQLite development support and PostgreSQL-compatible SQLAlchemy configuration.
- JWT role checks, password hashing, backend validation, rate limiting, CSP/security headers, SQLAlchemy parameterisation, upload extension/MIME allowlists, audit records, and protected admin operations.
- Automated API tests including customer-to-admin order synchronisation and rejection of unverified browser-side payment claims.

No business products, prices, testimonials, or administrator credentials are seeded. Create actual categories and products from the admin dashboard after setup.

## Run on Windows

From PowerShell in the project folder:

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
Copy-Item .env.example .env
```

Edit `.env` before the first run. At minimum, replace both secrets and set a real initial administrator email and password:

```ini
APP_SECRET_KEY=a-long-random-application-secret
JWT_SECRET_KEY=a-different-long-random-jwt-secret
ADMIN_EMAIL=owner@yourdomain.example
ADMIN_PASSWORD=use-a-long-unique-password
```

Then run:

```powershell
python -m backend.app
```

The development SQLite database is created at `backend/instance/paperplazo.db`. Sign in at `/admin/`, create categories and active products, then browse the catalog at `/`.

To run the automated tests:

```powershell
python -m pytest -q
```

## Firebase admin provisioning

Do not create a public admin-registration page. Admin access is granted only through a Firebase custom claim assigned by a trusted server-side process.

Create a service-account JSON file in a location outside the project directory, then point the environment to it before running the provisioning command:

```powershell
$env:GOOGLE_APPLICATION_CREDENTIALS="C:\path\to\paperplazo-service-account.json"
node scripts/provision-admin.js <FIREBASE_AUTH_UID>
```

Or store the path in `.env`:

```ini
FIREBASE_SERVICE_ACCOUNT=C:\path\to\paperplazo-service-account.json
```

Then run:

```powershell
node scripts/provision-admin.js <FIREBASE_AUTH_UID>
```

This assigns the custom claim:

```json
{ "admin": true }
```

To verify the claim without changing it:

```powershell
node scripts/provision-admin.js <FIREBASE_AUTH_UID> --verify
```

After assignment, the admin user must sign out and sign back in to refresh their Firebase ID token so the new claim is included in the token. The frontend should never assign `admin` from a client-side field. Customers must never be able to grant themselves admin access.

## Firestore product catalog

The customer storefront listens to the `products` collection in Cloud Firestore and displays documents where `isActive` is `true`. Product documents include `name`, `description`, `price`, `category`, `imageUrl`, `stock`, `sku`, `isActive`, `createdAt`, and `updatedAt`; the backend also stores existing catalog identifiers and display fields to preserve cart and product-page behavior. Timestamps are generated by Firestore.

Product writes continue through the authenticated Flask admin routes so the SQL-backed cart, inventory, and order workflows remain consistent. Firebase-authenticated admin requests mirror product and stock changes to Firestore. Product images are uploaded to the configured Firebase Storage bucket by the server; service-account credentials must remain outside the repository. The first Firebase-authenticated admin product-list request backfills existing SQL products that are not already in Firestore.

Deploy the restrictive Firestore and Storage rules and the active-catalog index with:

```powershell
firebase deploy --only firestore,storage
```

Public Firestore reads are limited to active products. Product writes require the Firebase custom claim `admin: true`; product image writes are similarly restricted by Storage rules.

## Production database

Install PostgreSQL and set `DATABASE_URL` in `.env` to a SQLAlchemy Psycopg URL, for example:

```ini
DATABASE_URL=postgresql+psycopg://paperplazo:strong-password@localhost:5432/paperplazo
```

Use a proper process manager/reverse proxy and HTTPS in production. Run controlled database migrations from `migrations/`; automatic schema creation is intended for local development only.

## Payment, email, and messaging status

Cash on delivery is the only checkout method that is operational in this project. The API deliberately rejects online-payment completion from the browser. A Razorpay webhook endpoint verifies its HMAC signature before accepting callbacks, but provider order creation/mapping has not been configured or tested because it requires real Razorpay account credentials and a public callback URL.

Email and WhatsApp delivery are not implemented. The project stores notifications inside the admin dashboard and provides integration-ready events for new orders, quote activity, order status changes, and low stock. Configure and test a transactional provider before claiming external notifications are live.

The forgot-password endpoint intentionally gives a non-enumerating response but does not send reset emails until a delivery provider and reset-token workflow are configured.

## Security notes

- Passwords use Werkzeug's salted password hashing.
- Tokens are role-scoped and short-lived (two hours for admins, eight for customers); only API `Authorization` headers are used, avoiding cookie-based CSRF exposure.
- Secrets and admin credentials are environment variables only; no frontend file contains them.
- Uploads are limited to JPG/JPEG/PNG/WEBP and PDF where appropriate, with a global 8 MB request limit.
- The app sets CSP, frame, content-type, and referrer-policy headers. Configure HTTPS, a production rate-limit store, and object/file storage before public deployment.
